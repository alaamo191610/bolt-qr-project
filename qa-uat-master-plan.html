Before starting

One clean, production-shaped environment

QA and UAT run in parallel only when both lanes point at the same seeded fixtures and neither is mutating the other's tenant.

  • Start API and web app; confirm health and a clean browser console.
  • Seed two isolated tenants, Alpha and Beta; test accounts only, never live data.
  • Have one active OWNER, MANAGER, STAFF, Super Admin, menu, promotion, table, and QR capability per tenant.
  • Run npm run test:all green before manual execution begins.
  • Record environment, browser/device, request ID, and repro steps on every failure.

Scope, tracks, and entry / exit criteria

What each track owns, and the conditions that open and close testing.

QA track · YAZAN

  • Correctness of the engine: transactions, state machines, idempotency.
  • Security boundaries: tenant isolation, token classes, roles at the API.
  • Platform control: Super Admin, MFA, provisioning, recent-auth gates.
  • Operations: backup/restore, migrations, database roles, capacity, shutdown, telemetry, TLS.
  • Method: crafted requests, negative paths, forced failures, evidence from logs and request IDs.

UAT track · ALAA

  • Can a customer scan, order, pay, and track without help?
  • Can an operator run a shift: menu, tables, QR, orders, analytics, pricing?
  • Does it work in Arabic and English, on a phone, with a keyboard, for a screen reader?
  • Business acceptance: real menu, real staff, real devices, peak-hour behaviour.
  • Method: run the product as the user would, no shortcuts, no dev tools.

Joint gates · both

  • Run together on one clean environment, same session.
  • End-to-end golden path, cross-tenant negative path, failure recovery.
  • Role matrix, billing limits, accessibility, rollback rehearsal.
  • Defect triage and the final Go / No-Go decision.

Entry criteria · testing may start

  • Release commit is tagged and frozen; no direct pushes during the run.
  • npm run lint, npm run typecheck, npm run build all pass.
  • npm run test:all is green on the release commit.
  • Alpha and Beta tenants seeded per the fixture sheet below.
  • Staging matches production shape: same Node range, same migrations applied.
  • Rollback command is documented and rehearsed at least once.

Exit criteria · release may ship

  • Every P0 case is Pass. No exceptions, no waivers.
  • Every P1 case is Pass, or has a written waiver signed by both leads.
  • Zero open tenant-isolation, authentication, or authorization defects at any severity.
  • Every joint gate case is Pass or explicitly waived in writing.
  • No case left in Blocked state.
  • Every Fail has a repro, an owner, a fix reference, and a retest result.
  • Both leads and the business owner have signed off below.

Suspension · stop the run

  • Any confirmed cross-tenant data leak: stop everything, fix, restart the affected sections.
  • Environment becomes unstable or the build changes mid-run.
  • More than three P0 failures in one section: the section is not ready for testing.
  • Fixtures are corrupted or the two lanes start colliding.
  • Resume only after a re-run of the entry criteria.

Defect severity, SLA, and reporting format

How a failure is classified, how fast it must be answered, and what a valid report contains.
SeverityDefinitionExamplesResponseBlocks release
S1 · CriticalData leak, money wrong, or the core journey is impossible.Cross-tenant read, duplicate order charged, checkout dead.Stop the run. Fix same day.Always
S2 · MajorA P0 journey works only with a workaround, or a role boundary is loose in the UI.Promotion applies twice then corrects, staff sees an owner-only button.Fix before ship. 24h.Always
S3 · ModerateA secondary feature is broken; the main journey survives.Analytics export mislabels a column, filter keeps stale state.Fix or written waiver. 48h.Waiver only
S4 · MinorCosmetic, copy, or polish with no functional impact.Untranslated tooltip, 2px misalignment at 320px.Backlog.No

A defect report must contain

  • Case ID from this plan, plus severity and track.
  • Environment, build/commit, browser and device.
  • Numbered repro steps starting from a clean session.
  • Expected result vs. actual result, stated separately.
  • Request ID, screenshot or recording, relevant log excerpt.
  • Tenant and account used, and whether it reproduces on the other tenant.

Retest rule

  • A fix is not accepted until the original case is re-run end to end.
  • Any S1 or S2 fix also triggers a re-run of its whole section.
  • A fix that touches tenant scoping, tokens, or totals re-triggers the joint gates.
  • Record the retest result in the case note, do not overwrite the failure history.

Waiver rule

  • Only S3 and S4, and only P1 or P2 cases, can be waived.
  • A waiver needs both leads plus the business owner.
  • It must state the risk, the affected users, and the fix date.
  • Write it in the case note prefixed WAIVED: so it exports.

What automation does not cover

  • Real camera scanning from a physical phone.
  • Printed QR legibility at actual print size.
  • Arabic RTL visual correctness and copy quality.
  • Screen reader announcement quality and usefulness.
  • Whether a busy operator can actually run a shift on it.
  • Restore rehearsal timing and rollback confidence.
